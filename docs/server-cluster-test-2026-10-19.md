초기 6대 시험 전용 구성에서는 **동시에 20명 체험, 나머지 방문자는 입장 대기**로 60명 모두 사진 분석, AI 질문 2개, AI 의견까지 완료했다. 입장 제한 없이 60명을 동시에 처리한 시험에서는 23명만 모든 단계를 완료했다.

- 20대의 합성 문진 정보와 저장소 예제 사진을 사용했다. 질문 생성 요청에는 흐림 증상 선택이 포함됐다. 실제 방문자 건강 정보나 클라우드 모델을 사용하지 않았다. 한국어 한 시나리오이며 사진 결과를 보고 사람이 문진 전체에 응답하는 브라우저 조작 시험은 아니다.

## 시험 중 수정한 서버 병목

처음에는 방문자마다 모든 Ollama에 준비 상태를 중복 조회하고 HTTP 클라이언트를 새로 만들면서 Windows 인증서 구성을 반복했다. 12명 시험에서도 준비 상태 12개가 모두 브라우저의 8초 제한을 넘는 현상을 확인했다.

1. `app/api/routes.py`: 같은 설정의 동시 Ollama 준비 조회를 하나로 합치고 결과를 3초간 캐시했다. 한 방문자의 연결 종료가 다른 방문자의 공유 조회를 취소하지 않도록 했다.
2. `app/core/http_client.py`, `app/services/llm.py`, `app/api/routes.py`: 인증서·호스트명 검증을 유지하는 SSL context를 재사용했다. HTTP 클라이언트와 연결 수명은 기존 방식을 유지했다.

해당 장치의 독립 클라이언트 생성 측정에서는 기존 약 484~676ms가 SSL context 재사용 시 약 0.65~1.05ms로 줄었다. 최종 12명 시험의 준비 상태 최대는 0.558초였다. 서로 다른 생성 응답과 시험 전용 사진 준비 조회 개선도 섞여 있으므로 전체 속도 향상을 이 코드 수정 하나의 효과라고 주장하지 않는다.

관련 회귀 검증은 다음 명령으로 **65개 통과**했다. 기존 Starlette 경고 1개가 있었고 `git diff --check`도 통과했다. 질문 내용·의료 판단·모델·시간 제한은 바꾸지 않았다.

초기 시험 종료 직후에는 시험용 서버를 자동 종료했고 8002 포트가 닫힌 것을 확인했다. 당시 기존 8000·8001 서버의 health는 정상, Ollama도 기존 프로세스가 실행 중이었다. 당시 공개 8000의 입장 정원은 **2명**이었다. 이 초기 시험 단계에서는 `.env` 및 공개 서버의 실행 설정을 바꾸거나 공개 서버를 재시작하지 않았다.

## 실제 운영 반영 — 학교 PC 5대, 체험 정원 12명

사용자의 실제 사이트 적용 요청 후, 시험 전용 중계 코드를 사용하지 않는 `app.main:app`을 localhost:8002에 새로 실행했다. 실제 앱의 사진 분석·분산 처리·질문 생성·의견·입장 관리를 그대로 검증했다.

6대·정원 20명으로 실제 앱을 시험했을 때 전체 완료 59/60명, AI 질문 응답 119/120개였고 질문 2개는 규칙 문항으로 대체됐다. 이어서 노트북의 Ollama와 사진 API, Tailscale ping이 모두 응답하지 않는 것을 확인했다. Tailscale 장치 목록의 `Online: true`만으로 실제 API 연결을 보장할 수 없었다. 정원 16명 재시험도 노트북 응답이 끊긴 상태에서 중단했으므로 정상적인 6대 용량 측정 결과로 사용하지 않는다. 앞선 시간 초과를 정원만의 영향으로 단정할 수도 없다.

공개 주소(`.env`의 `PRESENTATION_PUBLIC_URL`)는 그대로 유지하고, ngrok의 연결 대상만 새 서버 `http://127.0.0.1:8002`로 옮겼다. 기존 8000·8001 프로세스는 강제 종료하지 않았다. 기존 localhost:8000은 이전 설정의 별도 서버이므로 운영 확인은 공개 주소 또는 localhost:8002로 한다.

`.env` 원본은 `.env.bak-deploy-*`로 보관했다. 백업과 실제 장비 주소 설정은 Git 제외 대상이다. 메인 PC의 현재 절전 시간은 AC·DC 모두 0(안 함)으로 확인했다. 수요일에도 참여 학교 PC 5대의 전원·인터넷·Tailscale·Ollama가 유지돼야 한다. 노트북은 연결이 복구돼도 현재 구성에 자동으로 다시 추가되지는 않는다.

재부팅 등으로 다시 실행할 때는 학교 메인 PowerShell에서 다음을 사용한다.

```powershell
Set-Location -LiteralPath 'C:\eye_catch'
.\start-demo.ps1
```

이 스크립트는 기존 앱 실행기를 통해 localhost:8002를 준비하고, 설정된 AI 워커의 GPU 모델 적재와 원격 사진 API를 확인한다. 준비되지 않은 장비가 있으면 공개 연결 변경 전에 중단한다. ngrok이 이미 실행 중이면 동일 공개 주소의 upstream을 맞추고 외부 입장 정원을 확인한다. ngrok이 실행되지 않았으면 기존 설정과 공개 주소로 ngrok을 실행하며 이때는 창을 열어 둔다. 연결 변경 후 검증이 실패하면 이전 upstream 복구를 시도한다. 자동 복구 실패 상황을 의도적으로 재현한 시험은 수행하지 않았다.

현재 설치된 ngrok 3.37.6은 endpoint 갱신에 `PUT /api/endpoints`를 지원한다. 최신 문서의 `PUT /api/endpoints/:name`은 이 장치에서 405를 반환해, 로컬 API가 실제로 지원하는 경로를 확인하고 실행 스크립트를 맞췄다.

운영 반영 전 관련 Python 테스트 107개, 프런트엔드 테스트 183개가 통과했다. PowerShell 구문 검사와 워커 점검기의 문법·실제 연결 확인도 통과했다.

공개 주소에서 기존 Playwright와 설치된 Chrome을 사용해 모바일 390×844, 데스크톱 1280×900 화면을 확인했다. Browser 플러그인은 이 세션에 없어 Playwright를 사용했다. 실제로 대기 순번 1번 표시 → 새로고침 후 순번 유지 → 대기 취소 → 다시 대기 → 빈자리 발생 후 `/app` 자동 입장을 통과했다. 앱 제목과 첫 화면이 정상이고 프레임워크 오류 화면·콘솔 오류·모바일 가로 넘침이 없었다. 대기 및 모바일·데스크톱 앱 화면을 캡처해 육안으로 확인했다.

새 브라우저의 첫 접속에서는 ngrok 무료 서비스의 `Visit Site` 안내가 먼저 표시된다. 해당 안내를 실제로 누른 뒤 대기·입장 동작을 확인했다. 이 안내는 앱 자체의 대기 화면과 별개이며 남아 있다. 화면 검증 결과와 캡처는 `C:\Users\USER\.codex\visualizations\2026\10\08\01a11a0d-f79c-7491-8c23-6e4aa11c0401\deployment-20261019\`에 보관했다.
